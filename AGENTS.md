# Krtuworks SDK for Unreal Engine: instructions for coding agents

The Krtuworks plugin connects an Unreal Engine game or app (UE 5.3 or later) to Krtuworks: Krtuworks ID sign-in (guest, desktop browser, phone, console code, Steam), sessions, events, stats and achievements, cloud saves, remote config and A/B tests. Its core is plain C++ with no dependencies; the engine layer adds a game instance subsystem and Blueprint nodes.

## Before you start
- Check the project folder. A `*.uproject` file means Unreal: this plugin. `ProjectSettings/ProjectVersion.txt` means Unity: use `com.krtuworks.sdk` instead.
- Get the app's `krtuworks-config.json` from the partner console (the app's Credentials page) or from the Krtuworks MCP tool `get_setup`. Never write it by hand and never guess an id in it. It holds no secret, so it may be committed.

## Required steps
1. Put the plugin in the project's `Plugins/Krtuworks` folder from `https://github.com/krtuworks/krtuworks-sdk-unreal` (the tag of the version to use) and enable it.
2. Save the config as `krtuworks-config.json` next to the `.uproject` file. The build ships it with the game; a game build stops when it is missing.
3. Nothing to call at start: the SDK starts with the game (`UKrtuworksSubsystem`, a game instance subsystem). Development builds use TEST, Shipping builds LIVE; Project Settings > Plugins > Krtuworks SDK sets another environment. Test players and their data never reach LIVE.
4. The build label is the project version (Project Settings > Description > Project Version): give each released build its own.
5. Sign the player in with the Blueprint nodes (C++ can call the same through the subsystem):
   - `SignInAsGuest` once, after the game's age screen (birth date `YYYY-MM-DD`, 13 or older, with the Krtuworks ID Terms and Privacy Notice). The same device signs in again with no input.
   - `SignIn` opens Krtuworks ID the platform's way (desktop: system browser and a loopback return; iOS and Android: the system's sign-in session and the app's own scheme `com.krtuworks.<slug>:/callback`). A guest who signs in keeps their progress.
   - Consoles: `SignInWithCode` shows the player a code to enter at `id.krtuworks.com/link`.
6. To call the SDK from C++, add `"Krtuworks"` to the game module's dependencies in its `.Build.cs`. Blueprints need nothing more.
7. For Steam, also add the KrtuworksSteam plugin, in the same version as Krtuworks (it uses the engine's Online Subsystem Steam and the Steamworks SDK 1.57 or later). It registers itself; nothing to call.

## Rules
- Never call `krtu::Client` (from `GetClient()`) on the game thread: its calls block on the network. Use `UKrtuworksSubsystem::Run` or `RunErased`, which work on their own thread and answer on the game thread, or the Blueprint nodes.
- Game modules do not need exceptions or RTTI to use the plugin; the plugin's public headers do not throw.
- Events: `Track(Type, Data)` with a ready-made family (`screen_view`, `economy`, `item`, `performance`, `settings` …) or a type defined on the console. It returns `false` when nothing was kept (the module is off, statistics are switched off, or the player opted out); that is not an error.
- Stats and achievements: `IncrementStat`, `SetStat`, `UnlockAchievement`. They are kept on the device until the server has them and are never counted twice: do not add your own retry. With Steam, achievements also go to Steam, and ones support took back are cleared there.
- Steam stats: with KrtuworksSteam, stats mirror the server. The plugin sets the Steam stat to the server's value; never write Steam stats yourself. A stat is mirrored only when its Steam API name is set on the partner console.
- Steam Cloud: with KrtuworksSteam, the slots the console marks "mirror to Steam Cloud" are copied there as `krtuworks-<slot>.bin` by the SDK itself; keep Steam Auto-Cloud away from those files and do not write them yourself. When Steam's copy and the server's differ and nothing tells which is newer, the subsystem's `OnPlatformSaveConflict` fires: show both to the player and call the `Call` node's `resolveFile {slot, keep, current}` (`current` = the conflict's server version id; C++ `resolveFile`). Nothing in that slot moves until then.
- Leaderboards: the `SubmitScore` node (C++ `SubmitScore(Key, Value, Details)`; a whole number below 10^15, details 1 to 64 bytes, or empty for none because a Blueprint pin cannot be left unset) is kept on the device until the server has it, like a stat: do not add your own retry. `GetLeaderboards` gives each board with the player's score and rank, `GetLeaderboardEntries` (Scope `global` or `around`, Limit 1 to 100) the rows with Krtuworks usernames (empty name: show "Player"). A score the board's range refuses is dropped (`invalid_value`); while the module is off scores wait and reads fail with `module_disabled`. With Steam the plugin imports the player's own Steam row once per board and Steam account where the console turned the import on; it never writes to Steam boards.
- Rich presence (Steam, games only): declare the states and their params on the partner console, then call the `SetPresence` node with a state key and the values of its params when the player's activity changes. From C++ there is no subsystem `SetPresence`: call `Client::setPresence(key, params)` inside `UKrtuworksSubsystem::Run`, or use the `Call` node's `setPresence {key, params}`. Neither waits on the game thread. A refusal is an answer, not an error: check `bApplied` and `Reason` (`hidden` means the player turned presence off, `unknown_state` a key the console does not list, `param_missing` a value you did not give). Do not pass LEVEL or SESSION_MINUTES unless you want your own value: the SDK fills them from the open level and the play time and writes them again by itself. Do not write Steam's rich presence keys yourself, they would be cleared. `SetPresenceGroup(GroupId, Size)` adds Steam's party display to every state; `ClearPresence` removes the state when the player leaves the activity; the player's own switch is `SetPresenceVisible` and `PresenceVisible`, offer it in the game's settings.
- DLC ownership (games only): C++ `ownsDlc(Key)` (the DLC's product key from the console; the `Call` node's `ownsDlc {key}` answers `{owns}`). The server's answer for this launch wins; when it could not check, the Steam client's own answer (KrtuworksSteam asks `BIsSubscribedApp` for the DLC's AppID); else the last server answer kept on the device. `entitlements` and `refreshEntitlements` list the licences (`sku` `base` first; `status` `ACTIVE`, `REVOKED` or empty; `checked` for what the server confirmed this launch). Do not call `BIsSubscribedApp` or keep your own ownership flags.
- Steam accounts: progress mirrors only with Steam accounts the player allowed. The first Steam account a game sees with a Krtuworks ID is used without asking. Bind the subsystem's `OnPlatformLinkNotice` and show your own dialog for its `State`: `PENDING_CONSENT` (a second Steam account: "Also show your progress on this Steam account?", then the `Call` node's `answerPlatformConsent {allow}`; C++ `answerPlatformConsent(allow)`), `LIMIT` (a game uses at most 2 Steam accounts; the player removes one at id.krtuworks.com/apps), `MISMATCH` (this Steam account belongs to another Krtuworks ID; nothing is mirrored to it). Do not sync achievements yourself around it.
- Ready-made screens: call the `Ensure Player` node (C++ `UKrtuworksSubsystem::EnsurePlayer`) before the game starts instead of calling `SignInAsGuest` yourself. It shows the age and terms screen for a new guest, keeps a player under 13 offline, and never fails: it answers `OnSignedIn` or `OnOffline` (`Reason` `underage` or `unavailable`). `Sign In (Ready-made Screens)` signs in the platform's way with its own waiting or code screen. Save with `GetUi()->save(slot, bytes, base, name)` (off the game thread) to let the player choose when another device saved first; a `keptThere` answer carries the other save's bytes, which the game loads. Put the `Krtuworks Sign-in Button` and `Krtuworks Account Chip` widgets where the layout wants them. Change colours, corners and font with Project Settings > Plugins > Krtuworks SDK > `Theme` (`SetUiTheme` at runtime) and sentences with `TextOverrides` (`SetUiText`); with Steam, `bPlatformSaveConflicts` shows the Steam Cloud conflict itself, so leave it off only when the game handles `OnPlatformSaveConflict`. Do not copy or restyle the screens.
- Levels and deaths (`LevelStart`, `LevelComplete`, `Death` …) are for games only; in an app they do nothing.
- Time heat map: call `SamplePosition` (Blueprint `Sample Position`) from Tick with the player's position; the SDK sends at most one `position_sample` per `PositionSampleSeconds` (Project Settings, default 10) of active play. Do not throttle it yourself.
- Cloud saves: the `SaveFile` and `ReadFile` nodes. A conflict (`file_conflict`) carries the current version: let the player choose, do not overwrite.
- The SDK keeps its data under the project's Saved folder (`Krtuworks/`) and its secrets in the platform's secure storage. Do not move, copy or back up these files: a copied secret is refused on another device, and the SDK starts as a new device.
- Never put a server key or any other Krtuworks secret into game code. This plugin needs none.

## Verify
In the editor (Play In Editor) or a development build, run the `Validate` node (C++: `UKrtuworksSubsystem::Validate`). It checks the config, the build label and the platform, then makes a TEST round (sign-in, session, event, remote config, cloud save, progress, bug report) and writes each check to the `LogKrtuworks` log. The report's `bOk` ("Ok" in Blueprints) must be true. Each check is `PASSED`, `FAILED` (with its detail) or `SKIPPED` (a module that is off, an app with no save slots or no achievements). A build whose report is not green is not released in LIVE. On start the log says `Krtuworks SDK started (<type>, <environment>).`
